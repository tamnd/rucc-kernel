# The goal

There are six claims. Each has a number or a predicate, each can turn out false, and each is checked by a command in `rucc-kernel` rather than by somebody reading a serial log.

## 2.1 Unmodified

The source tree rucc builds is the pinned upstream tarball or tag, checked by SHA-256 before every build. Nothing is patched. No file is added to the tree, and nothing in it is regenerated by us. Generated files are produced by the kernel's own build from its own inputs, using the host tools of that era's container. That covers the Kconfig parser, `genksyms`' parser, `mkregtable`, the firmware and crc tables, and the `offsets.h` and `bounds.h` files made by compiling C to assembly.

Configuration is allowed, and it is always one of these:

1. **A `make` configuration target the kernel ships.** These are `tinyconfig`, `allnoconfig`, `defconfig`, `<board>_defconfig`, `allmodconfig`, `allyesconfig` and `randconfig` with a recorded `KCONFIG_SEED`.
2. **An in-tree fragment merged with `scripts/kconfig/merge_config.sh` or the `make <fragment>.config` form.** Examples are `kvm_guest.config`, `x86_debug.config` and `hardening.config`.
3. **The test fragment in `rucc-kernel/configs/`.** This is a short, published list of options that the boot rig needs and that `defconfig` may lack: serial console, devtmpfs, initramfs, virtio, KUnit, 9p. It is applied identically to the reference build, and it may only turn things on. Turning a feature off to avoid a rucc bug is a patch by another name and is forbidden. The single exception is `CONFIG_RUST=n` (section 2.7). The fragment's contents are listed in document 11.
4. **A distribution configuration.** For K5 and later, the graded "distro" configuration is the `config` file shipped in a pinned Debian 13 or Fedora kernel package, run through `olddefconfig`.
5. **The make variables the kernel documents:**
   - `CC`, `LD`, `AR`, `NM`, `OBJCOPY`, `OBJDUMP`, `HOSTCC`, `ARCH`, `CROSS_COMPILE`;
   - `KBUILD_BUILD_TIMESTAMP`, `KBUILD_BUILD_USER`, `KBUILD_BUILD_HOST`;
   - `O=`, `W=` (not graded), `LLVM=` (never with rucc).

   `CC` may carry exactly two things besides the program:
   - the persona, `-fgnuc-version=<v>`;
   - on cross builds, the target, as `--target=<triple>` or through a program name that implies it.

   `KCFLAGS` stays empty on every graded build. Anything that changes code generation must come from the kernel's own Makefiles.

These are never allowed:
- a patch, and a `sed` over the tree counts as one;
- a `.config` edit after `olddefconfig`, other than through the four sources above;
- a `KCFLAGS` or `KCPPFLAGS` value;
- a copied or regenerated file;
- a host tool swapped for one the era did not have;
- a test skipped because rucc fails it.

If the kernel needs a patch to build with rucc, rucc is wrong. That rule comes from the parent spec's section 14.0 and it is not relaxed here, not even for 1.0.

## 2.2 Configured the same

Let C_ref be the `.config` produced by `make olddefconfig` with the reference toolchain. Let C_rucc be the one produced with rucc and the same binutils, from the same starting configuration. The claim is that C_ref and C_rucc are identical apart from a fixed list of identity lines:
- `CONFIG_CC_VERSION_TEXT`;
- `CONFIG_GCC_VERSION`;
- `CONFIG_AS_VERSION`, if rucc's assembler persona differs from the reference binutils (document 05);
- the `CONFIG_*_VERSION` lines that follow from those.

Every other difference is a failure. That includes a difference in an option that looks harmless. The list of permitted lines is `config-divergences.toml` in `rucc-kernel`, and each entry states why it cannot change which code is compiled.

This is the kernel's version of the `pg_config.h` rule in the Postgres folder, and it matters more here. Kconfig gates dozens of features on compiler answers, and a green boot on a differently configured kernel is evidence about a different kernel. Examples:
- `CC_HAS_ASM_GOTO_OUTPUT`, `CC_HAS_NAMED_AS`, `CC_HAS_RETURN_THUNK`, `CC_HAS_IBT`;
- `CC_HAS_ZERO_CALL_USED_REGS`, `CC_HAS_AUTO_VAR_INIT_*`, `CC_HAS_COUNTED_BY`;
- `STACKPROTECTOR`, `CC_HAS_SANE_STACKPROTECTOR`, and more.

For kernels older than Kconfig's compiler probes, which means before 4.18, the same rule applies to the flags kbuild's `cc-option` calls decided on. `rk flags-diff` compares the command line of every translation unit, as described in document 05.6.

## 2.3 Passes

For each row R, version V and configuration C, let G(R, V, C) be the set of test units that pass when the reference toolchain builds V with C on R, in three runs out of three. The claim is that the rucc build passes every unit in G(R, V, C).

A **test unit** is one of these:

| Kind | Unit |
|---|---|
| boot | the boot itself, which passes when the serial console shows the rig's marker and the machine powers off within the time budget |
| KUnit | one suite, as `kunit.py` reports it |
| kselftest | one test program in one collection, as the TAP output reports it |
| LTP | one test case from the pinned runtest files |
| dmesg | the set of `WARNING:`, `BUG:`, `Oops`, `KASAN:`, `UBSAN:`, `KCSAN:` and `objtool`-style splats. The rucc kernel's set must be a subset of the reference kernel's, after normalizing addresses |
| objtool | the build log of x86-64 builds, which must contain no `objtool` warning from 4.6 onward |

Which kinds are graded on which version set is in document 11.2. Briefly:
- **Current:** everything, on x86-64 and AArch64.
- **Releases:** boot plus the smoke script, plus KUnit where it exists (5.5 onward).
- **Last points:** boot plus the smoke script.
- **Museum:** boot plus the smoke script, on i386.

The graded optimization levels are the kernel's own:
- `CONFIG_CC_OPTIMIZE_FOR_PERFORMANCE`, which is `-O2`;
- `CONFIG_CC_OPTIMIZE_FOR_SIZE`, which is `-Os`, on x86-64 and AArch64 current kernels only.

The kernel does not build at `-O0`. It relies on dead code elimination and constant folding to satisfy `BUILD_BUG_ON` and friends. So the parent spec's rule of passing at `-O0`, `-O1`, `-O2`, `-Os` and `-flto` does not apply. `-O3` exists as `CONFIG_CC_OPTIMIZE_FOR_PERFORMANCE_O3` on some kernels for some architectures, and it is not graded.

A unit in G that fails under rucc is a rucc bug until proven otherwise. "Proven otherwise" means a reduced reproduction showing the unit is flaky with the reference too, recorded in `exclusions.toml` with an issue.

## 2.4 All versions

Four version sets, defined fully in document 04. Here is how much each has to pass:

| Set | What | Rows | Graded | Cadence |
|---|---|---|---|---|
| Current | mainline HEAD and the latest rc, the latest stable, every kernel.org longterm head, every CIP SLTS head | X64, A64 all; X32 defconfig; R64 once it exists | everything in 2.3 | nightly |
| Releases | every non-rc tag from `v2.6.12` to the latest release, 114 today | X64 from `v2.6.12`; X32 for every tag; A64 from `v3.7` (arm64's first release) | build, boot, smoke, KUnit where present | full sweep weekly, new tags on the day they appear |
| Last points | the last point release of every stable and longterm branch ever (for example 2.6.32.71, 3.16.85, 4.4.302, 4.9.337, 4.14.336, 5.4.302) | X64 and X32 | build, boot, smoke | monthly |
| Museum | 1.0, 1.2.13, 2.0.40, 2.2.26, 2.4.37.11 | X32 only | build and boot to the rig's init | monthly |

The claim for a set holds when every member is green on one rucc commit, within one run of that set.

"Every version" does not include:
- every `-rc` tag;
- every point release of every branch;
- the 0.x kernels.

The rc tags and point releases are thousands of trees whose differences from the graded ones are small. The harness can build any of them on demand for bisection. The 0.x kernels were built by GCC 1.x with a Minix toolchain around them. Document 16 keeps 0.01 as an open question rather than a promise.

## 2.5 Very high performance

Performance has two parts, reported separately.

**The kernel rucc builds.** Measured on server3 (8 cores, x86-64) in a KVM guest with pinned vCPUs, the host otherwise idle. Both kernels are 7.2.x `defconfig` plus the test fragment, at `-O2`, booted with the same command line and the same initramfs.

| Measure | Target at K8 |
|---|---|
| each benchmark in the fixed set of document 12.2 | median within 5% of the reference kernel |
| geometric mean over the set | within 2% |
| boot to `init`, measured from the kernel's own timestamps | within 5% |
| `vmlinux` `.text` size | within 5% of the reference |
| kernel stack high water mark over the whole test run (`CONFIG_DEBUG_STACK_USAGE`) | no more than 10% above the reference |

AArch64 gets the same set measured under TCG as a sanity check. TCG numbers are not graded, because emulation cost swamps the difference being measured. Hardware for an AArch64 number is open question 6.

**The compiler, compiling the kernel.** Measured on the same machine, 7.2.x, `make -j8`, cold `ccache`-free build.

| Measure | Target at K8 |
|---|---|
| x86-64 `defconfig`, wall time | at least 1.5x faster than GCC |
| x86-64 `allmodconfig`, wall time | at least 1.3x faster than GCC |
| peak resident memory of any single rucc process | under 1.5 GB |
| the slowest single translation unit | under 3x GCC's time for that unit |

These figures are stricter than the Postgres folder's 1.2x, because the latest cost report already shows rucc compiling at about half GCC's time at `-O2`. What we must not do is spend that margin in the assembler. The kernel assembles far more text per unit than a normal program does, through inline assembly and `.S` files.

## 2.6 Four architectures

| Row | Kernel `ARCH` | rucc target | Reference | Where it runs |
|---|---|---|---|---|
| X64 | `x86_64` (`x86` from 2.6.24) | `x86_64-linux-gnu` in kernel mode | GCC of the era, from K0's containers | `qemu-system-x86_64` with KVM on server3 and gpc, TCG on CI |
| A64 | `arm64` | `aarch64-linux-gnu` in kernel mode | the same | `qemu-system-aarch64 -M virt`, KVM on the `ubuntu-24.04-arm` runners if they expose it, TCG otherwise |
| X32 | `i386`, then `x86` | `i686-linux-gnu`, which does not exist yet | the same | `qemu-system-i386` |
| R64 | `riscv` | `riscv64-linux-gnu`, which does not exist yet | the same | `qemu-system-riscv64 -M virt` with OpenSBI |

All builds are cross builds from a Linux x86-64 host, with rucc as the cross compiler and binutils for the target as the linker. The kernel does not run target programs at build time, so unlike Postgres a cross build is the natural build, not a compromise. Native builds on AArch64 hosts are recorded, not graded.

Any other architecture is **compile-only**. That covers s390, powerpc, loongarch, mips, arm and the others, and none of them has a rucc back end. They are not claimed. When a back end exists, `rk build --arch` works and the report lists the result.

## 2.7 What does not count

These results are not evidence for any claim:
- **A different kernel.** A boot of a kernel whose `.config` differs from the reference's beyond `config-divergences.toml`.
- **Bring-up flags.** A build that used either bring-up flag of document 00.
- **Nondeterminism.** A build from a rucc commit that does not produce byte identical objects twice in a row.
- **Weak graded runs.** A graded run that retried a failed boot, or used a looser timeout than the reference.
- **Different compiler input.** A performance number from kernels built with different `KBUILD_BUILD_*` values, which changes nothing in the code. Or one where the rucc kernel used `-Os` while the reference used `-O2`.
- **Rust.** A claim about a Rust driver. Rust code is not built, on either side.
- **Suspect toolchains.** A pass on a kernel version whose reference toolchain was not the one `personas.toml` names for that version.
